日期：2026-10-22。目标场景：一个人部署一个独立实例，一个实例只有一位站长；访客不需要成为平台用户。

## 结论（修复前）

初始化和注册限制已经按单租户实现，公开博客也已迁到根路径，旧地址有兼容转发。主要遗留问题集中在写作内容保护、网页编辑与插件数据的衔接，以及仍依赖多用户平台逻辑的互动和广场。

共记录 13 项问题：4 项 P1（优先修复）、9 项 P2（随后修复）。P1 指会丢失用户输入、覆盖已有内容，或让主要功能在目标部署模型下无法使用；不代表安全漏洞等级。

## P1：优先修复

### UX-01：访客互动要求站长登录，单租户下无法成立

**现象与影响**：文章向所有访客展示评论输入框、“发表评论”和点赞。评论与点赞 API 都要求已登录用户，但初始化之后又禁止任何新用户注册。结果是只有站长可以互动，读者输入评论后会跳到站长登录页；评论内容没有保留，也没有返回文章的路径。

**复现**：匿名打开公开文章 → 输入评论 → 发表评论 → `/login`。直接匿名调用评论创建接口返回 401。

**代码**：`src/components/blog/comment-section.tsx:68`、`:167`；`src/components/blog/like-button.tsx:41`；`src/server/api/blog.ts:533`、`:558`；`src/server/api/auth.ts:63`。

**建议**：将“站长账号”和“访客互动身份”分开。可以接入访客评论服务，或实现昵称/邮箱式留言及审核；点赞使用访客身份和限流。若暂不支持互动，应由站长开关控制并在前台隐藏入口。不要为解决互动而重新开放平台用户注册。

### UX-02：写作内容只存在组件内存，误离开后全部丢失

**现象与影响**：新建文章默认公开，主要动作只有“发布”。标题、正文和其他字段只有 React state，没有本地草稿恢复、自动保存或离开提醒。点击侧栏、返回列表或刷新即可丢失尚未保存的写作内容。私密文章可以充当手动暂存，但无法保护尚未执行保存的输入。

**复现**：写文章 → 输入标题与正文 → 点击“文章” → 再点击“写文章” → 表单为空，离开时无提醒。

**代码**：`src/components/dashboard/blog-editor.tsx:41`、`:102`、`:148`、`:169`。

**建议**：先增加按文章区分的本地草稿、恢复提示和脏状态离开保护；之后再明确区分“保存草稿 / 发布 / 更新”，并显示保存状态。处理登录过期时也应保留当前输入。

### UX-03：网页编辑器保存会覆盖插件或迁移写入的手工摘要

**现象与影响**：编辑器的文章类型包含 `summary`，但加载时没有保存它，也没有编辑摘要的控件。保存时总是提交正文而不提交摘要；服务端只要收到正文且未收到摘要，就重新生成摘要。即使只想改标题，也会覆盖之前通过插件或迁移保存的手工摘要，且不会提醒。

**复现**：通过 API 创建带 `summary: "我手工填写的摘要"` 的文章 → 网页打开编辑并保存 → 详情接口返回由正文生成的新摘要。

**代码**：`src/components/dashboard/blog-editor.tsx:29`、`:67`、`:108`；`src/server/blog/articles.ts:356`。

**建议**：编辑器加载、展示并提交摘要，区分自动摘要与手工摘要；若没有摘要编辑功能，保存其他字段时也应保留已有手工摘要。增加“插件创建 → 网页修改 → 插件读取”的往返回归测试。

### UX-04：保存某个设置分区，会覆盖其他分区尚未保存的输入

**现象与影响**：外观、个人资料、又拍云放在同一页，却采用不同保存按钮。`guard()` 成功后调用全量 `reload()`，重新设置主题、首页介绍、关于、友链、邮件偏好和 CDN 表单。上传头像或保存昵称会悄悄清掉未保存的长篇介绍；保存 CDN 也会重置外观输入。

**复现**：设置 → 输入一段首页介绍，不点击“保存外观” → 点击“保存资料” → 首页介绍恢复为服务器旧值。

**代码**：`src/components/dashboard/blog-settings.tsx:107`、`:120`、`:141`、`:156`、`:490`、`:575`。

**建议**：各分区独立维护加载、保存和脏状态；保存资料只更新资料，保存 CDN 只更新 CDN。刷新服务器布局时不要覆盖其他尚未保存的表单。

## P2：随后修复

### UX-05：自定义页面创建之后无法在后台编辑，空白草稿也无法继续完成

**现象与影响**：页面管理只有创建与删除，没有编辑、预览、发布状态修改、导航开关修改或导航排序。空内容页面自动变成 draft，但后台没有继续填写和发布的入口。有内容则直接发布，不能显式选择草稿。已有内容改一个错字，也只能绕过界面调用 API 或删除重建，影响链接稳定性。

**依据**：完整检查 `src/components/dashboard/manage-static.tsx:63`、`:135`；服务端已经有 `page/update` 和 `page/reorder`，但 UI 未接入。

**建议**：复用编辑器完成页面的创建、编辑、草稿预览、发布和导航管理；列表加入“查看 / 编辑”，展示中文状态。

### UX-06：互动邮件通知只有偏好存储，没有邮件发送实现

**现象与影响**：设置承诺“有人点赞或评论时发邮件提醒”，并提供立即发送、每日摘要、随机发送。实际实现只更新两列配置；项目中没有发送邮件、邮件服务配置、任务队列或摘要调度。用户会收到保存成功的反馈，却永远等不到邮件。

**代码**：`src/components/dashboard/blog-settings.tsx:406`；`src/server/blog/site.ts:211`。检索 `src` 与依赖清单，未发现发送实现。

**建议**：在邮件功能实现前移除或明确禁用此设置；实现时提供发信配置、测试邮件及失败反馈，并与新的访客评论方案一起设计。

### UX-07：编辑器清空封面后提示成功，但旧封面仍然存在

**复现**：编辑已有封面的文章 → 删除封面 URL → 保存 → 重新编辑，原 URL 仍在。

**原因**：客户端使用 `coverUrl: coverUrl || undefined`，JSON 序列化后丢弃这个字段；服务端按局部更新语义保留旧封面。

**代码**：`src/components/dashboard/blog-editor.tsx:122`；`src/server/blog/articles.ts:357`。

**建议**：明确区分“不修改”和“清空”，清空时提交空字符串；提供移除封面动作和缩略图预览。

### UX-08：博客广场保留多用户文案，且文章集合取决于隐藏的旧平台标记

**现象与影响**：主题导航、页脚、默认关于页仍链接“博客广场”，页面写着“发现大家的公开文章”。广场查询要求 `sync_to_main_profile = 1`，网页编辑器却固定提交 `false`。所以同一篇公开文章可以在首页出现、在广场消失；插件创建和网页保存还可能改变这种表现，用户无法在界面理解或控制。

**代码**：`src/app/blog-plaza/page.tsx:30`；`src/components/blog/site-footer.tsx`；`src/components/blog/mizuki-shell.tsx:164`；`src/components/dashboard/blog-editor.tsx:121`；`src/server/blog/articles.ts:584`。

**建议**：独立博客移除公开的广场入口，旧路径可以兼容转到首页或文章索引。如果需要“精选”，将其作为站内栏目，使用显式可管理的精选字段。插件兼容需要的旧 API 字段继续保留。

### UX-09：初始化站点名称没有用于主要博客界面，所有页面共用产品标题

**现象与影响**：初始化填写站点名称后，博客外壳展示昵称，简约主题拼接“昵称的博客”；主页、文章页等浏览器标题始终为 Wind Blog。打开多篇文章时标签页无法分辨，书签和分享也没有文章身份。后台没有修改站点名称的常用入口。

**实际验证**：创建名为“体验审计测试博客”的站点后，首页与文章 HTML 的 `<title>` 都是 `Wind Blog`。`SiteHeader` 会客户端读取站点名称，但主要三套博客外壳不使用它。

**代码**：`src/app/layout.tsx:10`；`src/app/(site)/layout.tsx:41`；`src/components/blog/simple-shell.tsx:44`；`src/server/api/auth.ts:127`。

**建议**：统一站点名称配置，前台品牌和 metadata 使用该配置；文章使用“文章标题 · 站点名称”，固定页使用各自标题，并为公开文章补分享描述与 canonical。受保护内容的 metadata 继续遵循可见性规则。

### UX-10：常用账户操作缺席，登录无法回到原来的操作位置

**现象与影响**：`/manage` 的侧栏和设置页没有退出登录、修改密码入口；退出藏在旧广场使用的 `SiteHeader` 菜单里。改密码虽有 API，UI 未接入。管理布局跳登录时只记录 `/manage`，登录表单又完全忽略 `next`，始终前往旧 `/dashboard/blog` 再转到文章列表。

**代码**：`src/components/dashboard/blog-admin-shell.tsx:37`；`src/components/dashboard/blog-settings.tsx:472`；`src/components/site-header.tsx:98`；`src/app/manage/layout.tsx:12`；`src/components/auth/login-form.tsx:24`。

**建议**：后台增加明确的账户菜单和修改密码表单；登录保留并校验站内返回地址；会话过期时提供重新登录和恢复草稿流程。独立部署还应记录忘记密码时可执行的本地恢复方法。

### UX-11：请求失败被展示成加载中、零数据或空编辑器

**现象与影响**：设置关键请求失败时，界面一直“加载中”；数据概览请求失败时显示全 0，像真实统计；文章加载失败仅 toast，随后仍渲染可保存的空表单。页面和静态站点列表请求失败则保持空列表。用户无法判断到底没有内容，还是网络/会话出了问题，也无法就地重试。

**代码**：`src/components/dashboard/blog-settings.tsx:107`、`:189`；`src/components/dashboard/manage-analytics.tsx:24`、`:30`；`src/components/dashboard/blog-editor.tsx:76`、`:140`；`src/components/dashboard/manage-static.tsx:38`。

**建议**：对关键请求区分 loading / error / empty / success；错误页面提供重试，文章加载成功前禁止保存；401 给出重新登录路径并保留输入。

### UX-12：页面和静态站点删除没有确认，也没有恢复入口

**现象与影响**：文章、分类删除已有确认弹窗，但页面和静态站点列表的垃圾桶按钮直接调用删除接口。评论删除同样直接执行。缺少确认、撤销和回收站，易误触；页面删除重建也可能改变 URL。

**代码**：`src/components/dashboard/manage-static.tsx:148`、`:202`；`src/components/blog/comment-section.tsx:91`。对照：`src/components/dashboard/manage-articles.tsx:187` 已有确认弹窗。

**建议**：优先统一带对象名称的删除确认，说明评论子树等连带影响；后续考虑回收站或限时撤销。

### UX-13：评论超过 50 个根节点后不可访问，评论数也不准确

**现象与影响**：前端固定请求 `page: 1, pageSize: 50`，不读取返回的 total，也没有加载更多或翻页。标题使用 `comments.length`，只计算当前页根评论，不包括回复。历史迁移的评论超过一页时，剩余内容在网页中没有入口。

**代码**：`src/components/blog/comment-section.tsx:55`、`:158`；`src/server/blog/comments.ts:79`。服务端已有根节点分页及回复树支持。

**建议**：明确区分根评论分页与总评论数，接入加载更多；获取失败时显示错误，不要显示成“还没有评论”。访客互动方案调整时一并处理。

## 其他低优先级观察

- 首页和后台搜索无结果时仍显示“还没有文章”，容易让人误以为文章丢失；应该区分空站与筛选无匹配。广场切换排序还会丢弃关键词。
- 分类删除确认说文章“不再归属此分类”，实际会移入默认分类，应说明具体去向：`src/components/dashboard/manage-categories.tsx:194`、`src/server/blog/categories.ts:165`。
- 图片和头像上传控件使用 `accept="image/*"`，但服务端只支持若干位图格式；图床未配置时控件仍可用，没有提前引导到配置。实际云存储连接未测试。
- 三套主题需要分别验收功能一致性。简约主题未呈现配置中的社交链接；Mizuki 的文章目录放在侧栏，移动端是否有等价入口需要专项确认。本次未将其计为已经复现的移动端问题。
- `README.md` 仍宣传作者管理、审核、图片申请等平台式后台；`AGENTS.md` 仍描述已不存在的 `/blog/[username]/layout.tsx`，会误导后续维护。

## 单租户整理方向

保留“唯一站长管理内容 + 访客公开阅读”的边界。注册封禁、根路径博客和旧地址兼容可以沿用；用户 ID、旧 API 路径和插件字段不需要为了界面简化而破坏兼容。

1. 先保护内容：本地草稿、离开提醒、摘要保留、独立设置保存、删除确认。
2. 再闭合功能：明确访客互动方案，补页面编辑，移除尚未实现的通知承诺，补账户操作与错误恢复。
3. 最后统一表达：站点名称、页面标题、主题功能、空状态、导航；收起广场、作者、开通和上传申请等旧平台概念。
